# 积极分子考试锦囊

一个面向入党积极分子考试的知识记忆与自测 Web 应用。单文件前端，零依赖，零构建，打开即用。

**在线访问**：https://8935630.github.io/jinnang/

---

## 一、项目用途

学校下发的《学生党员和入党积极分子应知应会知识汇编》是一份 23 页的 PDF，包含 120 个知识点，其中 84 个标注 ★ 为"必须熟练掌握的核心基础知识"。PDF 的问题是：只能顺序翻阅，无法检索，无法自测，也不知道自己哪里没记住。

这个项目把这份 PDF 转成了一个可检索、可自测、能跟踪记忆状态的应用，解决三件事：

1. **查**——120 个知识点按 6 大板块归类，支持关键词搜索、只看 ★ 核心
2. **背**——仿百词斩的挖空自测，答完自评掌握程度，系统按遗忘曲线安排下次复习
3. **排**——根据考试日期倒推每日任务量，给出背诵时段建议

## 二、功能模块

| 模块 | 说明 |
|---|---|
| 知识库 | 120 个知识点分类展示，原文加粗处同步保留，支持搜索与 ★ 筛选 |
| 背诵检测 | 165 道挖空题，翻卡式自测，三档自评（记得/记不清/完全没听过） |
| 记忆时间表 | 艾宾浩斯复习节点 + 考试日期倒推排期，未来 14 天任务可视化 |
| 错题本 | 自评为"记不清/完全没听过"的题自动汇入，按错误次数排序 |
| 统计 | 各板块进度、★ 核心完成度、进度导出导入 |
| 云同步 | 基于 GitHub Gist API，电脑手机双向同步 |

## 三、设计思路

### 3.1 为什么是单文件零依赖

这个应用的使用场景是**考前突击**：用户可能在宿舍用电脑、在路上用手机、在考场外最后翻一眼。任何需要安装、登录、等加载的环节都会让人放弃使用。

所以技术选型做了两个决定：

- **不用框架**。整个应用是一个 `index.html`（1468 行，含 CSS 与 JS）加一个数据文件 `kb-data.js`（1569 行）。没有 npm、没有构建步骤、没有 node_modules。双击 HTML 文件就能跑，部署到 GitHub Pages 也只是把两个文件扔上去。
- **不用后端**。学习进度存浏览器 `localStorage`，跨设备同步借用用户自己的 GitHub Gist 当存储。这样不需要服务器、不需要数据库、不产生任何运维成本，数据也完全在用户自己账号下。

代价是放弃了组件化和类型检查。对一个 3000 行、单人使用、生命周期约一个月的工具，这个取舍是合理的。

### 3.2 间隔重复：为什么要压缩遗忘曲线

标准艾宾浩斯间隔序列是 `5分钟 → 30分钟 → 12小时 → 1天 → 2天 → 4天 → 7天 → 15天 → 30天`。

但考试是有截止日期的。如果用户距考试只剩 5 天，而某个知识点已经进到"15 天后复习"的档位，那它在考前就再也不会出现——这显然不对。

所以实现里加了一步**间隔截断**：

```javascript
function effIntervals(){
  var ex = store.conf.examDate;
  if(!ex) return IV;
  var left = Math.max(1, Math.floor((new Date(ex+'T23:59:59') - Date.now())/86400000));
  var out = [];
  for(var i=0;i<IV.length;i++){
    if(IV[i] < left*24*60) out.push(IV[i]);   // 只保留考前能走完的档位
  }
  if(out.length < 3) out = IV.slice(0,3);      // 至少保留三档，避免退化成单档
  return out;
}
```

考试日期一填，超出剩余天数的档位自动失效，保证每个知识点考前至少还能复习两轮。这是把一个通用记忆算法适配到"有 deadline 的备考"场景的关键一步。

### 3.3 跨设备同步：逐题双向合并

同步最容易出的问题是**覆盖**：手机答了 20 题，电脑答了 15 题，谁后同步谁把对方覆盖掉。

因为用户在两端都会用，所以这里不能用"整体覆盖"，必须做**逐题级别的合并**。每道题的状态里带一个 `last`（最后作答时间戳），合并时按题取时间较晚的一方：

```javascript
function mergeStore(a, b){
  var out = normalize({}), ids = {};
  for(id in a.items) ids[id] = 1;
  for(id in b.items) ids[id] = 1;

  for(id in ids){
    var x = a.items[id], y = b.items[id], pick, src;
    if(!x){ pick = y; src = b; }
    else if(!y){ pick = x; src = a; }
    else if((x.last||0) >= (y.last||0)){ pick = x; src = a; }   // 取较晚的一方
    else { pick = y; src = b; }
    out.items[id] = pick;
    if(src.mistakes[id]) out.mistakes[id] = src.mistakes[id];   // 错题计数跟随胜方
  }
  // 配置项（考试日期等）整体取 confAt 较晚的一端
  out.conf = (a.confAt||0) >= (b.confAt||0) ? a.conf : b.conf;
  out.confAt = Math.max(a.confAt||0, b.confAt||0);
  return out;
}
```

每次同步的完整流程是 **拉取云端 → 逐题合并 → 推回云端**，而不是直接推送。这样第二台设备上线时不会把第一台的进度冲掉。

还有一个细节：累计作答次数**不存累加器，而是从各题的 `r/w/f` 计数现场派生**。因为如果存累加器，两端合并后数字会翻倍。

```javascript
function calcStats(){
  var done = 0, correct = 0;
  for(var id in store.items){
    var it = store.items[id];
    done += (it.r||0) + (it.w||0) + (it.f||0);
    correct += (it.r||0);
  }
  return { done:done, correct:correct };
}
```

合并逻辑写了 13 项断言验证，覆盖同题取新、各自独有题保留、错题跟随、配置取新、**交换律**（A 合 B 与 B 合 A 结果一致）、原对象不被修改。

### 3.4 从 PDF 提取加粗：解析内容流

知识库要求"源文档加粗处同步加粗"。这件事比预期麻烦。

`pdftotext` 只能导出纯文本，不带字体信息。查 PDF 的字体表，发现里面有一个 `DengXian-Bold`，但它的 `FirstChar`/`LastChar` 都是 32——只包含空格字符。也就是说**中文加粗不是靠粗体字体实现的**。

进一步解析页面内容流，找到了真正的机制：**合成加粗**（synthetic bold），用 `2 Tr` 文字渲染模式（填充 + 描边）模拟粗体。全文共出现 221 次。

于是写了个 Perl 脚本解析内容流：展开 `ObjStm` 对象流、解析 `ToUnicode` CMap 做字形码到 Unicode 的映射、跟踪 `q`/`Q` 图形状态栈以正确判断每个文本串的渲染模式：

```perl
while ($c =~ m{
      (?<q>q)(?![A-Za-z])
    | (?<Q>Q)(?![A-Za-z])
    | (?<tr>\d+)\s+Tr(?![A-Za-z])
    | /(?<tf>\w+)\s+[\d.]+\s+Tf(?![A-Za-z])
    | \[(?<tj>(?:[^\[\]\\]|\\.)*)\]\s*TJ(?![A-Za-z])
    ...
}gsx) {
    if (exists $m{q}) { push @stack, [$tr,$cf]; next; }        # 保存图形状态
    if (exists $m{Q}) { my $p = pop @stack; ($tr,$cf) = @$p if $p; next; }
    if (exists $m{tr}) { $tr = $m{tr}+0; next; }               # 渲染模式
    ...
    next unless $tr == 2;                                       # 只取合成加粗
}
```

提取出 221 次渲染（200 处含文字 + 21 处是空格），与 `2 Tr` 出现次数完全吻合，证明提取完整。

**归属到知识点时踩了两个坑**，都是真实数据的脏处：

1. **目录页混进了正文流**。目录里也有 1–120 的编号，按顺序扫描会在目录里就把游标推到 120，正文全部失配。解决办法是定位"党的性质"的**第二次**出现作为正文起点。
2. **页脚页码是裸数字**，会被误认成条目编号。加上"编号必须带小数点且严格递增 1"的约束后解决。

最终 88 处加粗全部正确落位，零遗漏。

### 3.5 响应式：三种设备三套布局

目标设备是 iPhone、iPad、Windows 桌面，断点设在 700px 和 1024px：

- **< 700px**：单列，底部 Tab 栏导航，适配 `env(safe-area-inset-bottom)` 避开 iPhone 底部手势条
- **700–1024px**：双列网格，仍用底部导航
- **≥ 1024px**：左侧边栏 + 主内容区，隐藏底部栏

开发中发现并修复的两个真实布局 bug：

- `.app` 容器的左右内边距只写在 `@media (min-width:1024px)` 里，导致移动端和平板下内容直接贴着屏幕边缘
- 开启云同步后，顶栏三个标签（★ 进度 / 距考试天数 / 同步状态）在窄屏下溢出 20px。修法是窄屏隐藏次要标签、同步状态改用短文案（"已同步"而非"已同步 今天 14:30"），完整信息移到 `title` 属性

数据结构：

```javascript
// 知识点
KB({ id:1, no:1, cat:'dangzhang', star:1, title:'党的性质',
     body:['中国共产党是<b>中国工人阶级</b>的先锋队……'] });

// 题目：题干中 [方括号] 内的内容会被自动转为挖空
q(1, '党章 · 填空背诵',
  '中国共产党是[中国工人阶级]的先锋队，同时是[中国人民和中华民族]的先锋队。',

```

题干的挖空在运行时解析，不需要预处理步骤：

```javascript
function prepQuestions(){
  for(var i=0;i<Q.length;i++){
    var qq = Q[i], ans = [], stems = qq.stem.split(/(\[[^\]]*\])/g);
    qq.stemHTML = stems.map(function(seg){
      var m = seg.match(/^\[([^\]]*)\]$/);
      if(m){
        ans.push(m[1]);
        return '<span class="blank" data-a="'+m[1]+'">…</span>';
      }
      return seg;
    }).join('');
  }
}
```

## 五、关于 vibe coding

这个项目完整经历了"用自然语言描述需求 → AI 实现 → 真机验证 → 发现问题 → 迭代"的循环，没有手写一行代码。

过程中有几点体会：

**AI 不会主动验证，必须要求它验证。** 前几轮改动后页面看起来正常，但实际有未定义的函数引用、重复的变量声明覆盖、`@keyframes` 被误删而动画仍在引用。这些问题是在用无头 Chrome 实际加载页面、捕获 console 错误后才暴露的。后来固定了"每轮改动后跑一遍六个视图 + 捕获 window.onerror"的验证流程。

**脏数据的问题 AI 第一遍几乎一定做错。** PDF 加粗提取这件事，前三版归属算法都失败了：第一版贪心匹配把"发展"错配到隔壁条目；第二版段落定位有 35 个失配；第三版在目录页混入正文时整体错位。每一版都是先跑出结果、人工审计发现不对、再定位根因。最终版本才做到零遗漏。

**测试写错了比代码写错了更危险。** 验证合并逻辑时有一项断言失败，第一反应是改代码，核对后发现是我自己的期望值算错了（题目的 `r=0` 而我按 `r=1` 写的期望）。如果当时直接改代码去迁就错误的断言，就会引入真实的 bug。

**小结**：vibe coding 把实现成本压得很低，但把验证的重要性放大了。能快速产出不等于产出正确，这个项目里真正花时间的部分不是写代码，而是设计验证方式、读验证结果、定位根因。
